Operations has a payment EOD batch that can finish cleanly on a first run but becomes financially inconsistent when the same cycle is resumed. Repair the implementation under `/app/eod` so the batch follows the business contract in `/app/eod/contracts/eod_contract.md` for both a clean run and a resumed run. The shell runner is the batch controller, `/app/eod/cobol/paydup.cob` and `/app/eod/cobol/payexec.cob` remain the COBOL decision programs described by the contract, `/app/eod/sql/schema.sql` defines the persistent model, and `/app/eod/state/payment_eod.db` is the authoritative SQL state. Do not replace the COBOL decision programs with another language.

The command `/app/eod/bin/run_eod.sh` must leave `/app/eod/state/payment_eod.db` internally consistent and write `/app/eod/out/reconciliation.json` on every completed invocation. When reconciliation permits publication it must also write `/app/eod/out/customer_response.csv` and `/app/eod/out/clearing_submission.csv`; otherwise those two files must be absent. `/app/eod/out/success_authorization.json` must exist only when the run is definitively complete. CSV schemas are `payment_id,source_ref,outcome,reason` and `payment_id,source_ref,amount_cents,currency`. The reconciliation JSON must contain `cycle_id`, `status`, `original_count`, `final_count`, `original_value_cents`, `response_value_cents`, `internal_success_count`, `internal_posting_count`, `external_success_count`, `reservation_count`, `clearing_count`, `reserved_debit_cents`, `clearing_value_cents`, `external_fee_tax_cents`, `ledger_debits_cents`, `ledger_credits_cents`, and `difference_count`. The success JSON must contain `cycle_id`, `business_date`, `source`, `run_id`, and `status`.
